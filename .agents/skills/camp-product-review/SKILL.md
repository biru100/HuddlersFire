# 불멍 놀이터 제품 검토

## 출발점과 범위

[의도 기준](../../../docs/project-intent.md)의 관련 ID·근거·상태와 현재 요청·답변을 먼저 읽는다. [제품 방향](../../../docs/product-direction.md)은 경험 설명으로 함께 본다. 새 답변이 기존 기준을 바꾸면 의도 기준의 변경·충돌 절차를 적용한다. 제안을 사용자 결정으로 바꾸지 않는다.

[구조 문서](../../../docs/architecture.md), [최근 제품 검토](../../../docs/product-review.md), [검증 기록](../../../docs/validation.md)을 필요한 부분만 읽고 코드로 현재 사실을 확인한다. 처음에는 자체 구현 전체의 모듈과 사용자 흐름을 훑는다. 이후에는 바뀐 흐름과 영향 범위를 중심으로 검토하고, 공통 상태·입퇴장·제품 방향이 바뀌면 범위를 넓힌다. 매번 모든 소스·의존 패키지를 정밀 감사하지 않는다.

## 구현과 경험의 대조

- 입장→친구 알아보기→쉬기/놀기→연결 복구→퇴장 흐름에서 실제 동작과 안내를 비교한다. 코드 근거와 사용자가 받는 영향을 함께 남긴다.
- 조용한 동석, 대화와 놀이, 개발 중 동행, 게임 소개를 모두 고려하되 현재 요청과 무관한 전용 기능을 자동으로 추가하지 않는다. 네 장면의 동일 비중·개발 순서는 확정되지 않았다.
- 상태·공간·개인 선택을 서로 대신하는 것으로 해석하지 않는다. 현재 승인 범위와 보류 항목은 의도 기준에서 읽고, 과거 검토가 제안한 우선순위를 그대로 재사용하지 않는다.
- 장난감의 밀림·연쇄 들기 등 승인된 놀이를 ‘온기’라는 추상적 이유만으로 제거하지 않는다. 충돌이 있으면 누가 어디서 무엇을 경험하는지 구체적인 사례로 설명한다.
- 테스트·빌드·Canvas·루프백 RTC 결과는 기술 근거다. 측정은 의도를 실현할 방법의 근거이며 목적을 자동 변경하지 않는다. 실제 인터넷 환경·커뮤니티에서 편안했는지는 따로 확인하고 미확인 범위를 남긴다.

## 의도 확인의 반복

검토한 사실 → 확정 의도와의 차이 → 다음 결정 순으로 정리한다. 코드·자료로 알 수 있는 사실과 합리적으로 정할 구현 세부는 직접 해결한다. 사용자 결정 없이는 다음 설계가 정해지지 않을 때만 구체적인 상황, 선택의 결과 차이와 질문 이유를 제시한다.

AgentHub에서는 현재 세션의 질문 허용 조건·블록 형식·개수·턴 종료 규칙을 우선한다. 답변에 의존하는 설계는 답이 올 때까지 확정하지 않는다. 이미 받은 답이나 승인한 범위를 반복해서 묻지 않고, 의문이 없으면 질문 없이 검토를 마친다.

답을 받으면 사용자 결정만 제품 기준에 반영하고 다음 관련 검토에서 다시 대조한다. 질문 회차나 개수를 목표로 삼지 않는다. 검토에서 발견한 추가 기능·별도 수정은 승인 범위와 구분하며, 기존 승인으로 진행 가능한 일은 불필요하게 멈추지 않는다.

## 남길 결과

작업 규모에 맞춰 검토 범위, 코드 근거, 사용자 영향, 필요한 후속 결정, 검증 한계를 전달한다. 지속적으로 참조할 의도와 차이는 제품 문서에 갱신하고 일회성 실행 결과는 검증 기록에 둔다. 같은 규칙을 스킬과 여러 문서에 복제하지 않는다. 계획만 요청받았다면 이 기록을 포함해 파일을 변경하지 않는다.

의도·하네스·스킬 자체를 수정할 때만 [행동 사례](references/intent-cases.md)를 읽고 현재 규칙에 대입한다. 일반 기능 작업마다 이 전체 사례를 재검토하지 않는다.
