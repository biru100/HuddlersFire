# P2P 상태 전송량 개선 비교

2026-11-04. 앞부분은 구현 전 후보 비교 기록이고, 마지막의 **v9 적용 코드 비교**는 구현 후 결과다. 둘 다 오프라인 데이터량 비교이며 실제 인터넷 회선 속도·지연·FPS를 측정한 결과가 아니다.

## 재현

```powershell
cd web
node tests/measure-p2p.mjs
```

측정 코드: [measure-p2p.mjs](../web/tests/measure-p2p.mjs). 이번 실행 원본 JSON: `outputs/p2p-payload-benchmark.json` (로컬 생성물).

Node v24.21.0, 통신 규약 v8 소스 기준. 16명, 수신 참가자 15명, 시나리오당 30초, 초당 15회의 주기적 발행 호출이다. 실제 `simulateWorld`, `CampNetwork.publishWorld`, 무기 시나리오의 `handleCommand`를 실행하고 소켓 대신 생성되는 메시지 바이트를 집계했다. 동일 메시지를 15명에게 전달하는 값으로 환산했다.

이동 인원은 매 프레임 이동 **입력을 제공한 인원**이다. 방향은 1초마다 바뀌고 충돌·추락·복귀는 실제 물리를 따른다. 16명이 항상 모두 이동하는 최악 조건이나 실제 커뮤니티 이용 분포를 대표하지 않는다. 무기 시나리오는 총·눈뭉치·폭탄을 나눠 선택한 후 0.8초마다 사용을 시도하며 실제 쿨다운·피격·명령 제한이 적용된다.

## 비교 후보

1. **현재 방식:** 주기적인 전체 JSON 상태와 실제 명령 성공 직후의 전체 신뢰 상태 발행. 기존 대기 중 중복 전송 억제를 포함한다.
2. **변경분 JSON:** 일반 프레임은 확인된 전체 상태를 기준으로 바뀐 플레이어 필드만 전송한다. 필드는 이름 대신 스키마상의 번호를 사용한다. 모든 전체 신뢰 상태는 현재 JSON을 그대로 유지한다.
3. **변경분 + 전체 상태 경량화:** 2번에 더해 전체 상태도 고정 필드 순서의 JSON 배열로 전송한다. 데이터 내용·정밀도·전체 상태 발행 횟수는 유지한다. 변경분보다 전체 경량 상태가 작으면 전체를 선택한다.
4. **단순 바이너리 후보:** 변경분에 태그·길이·float64를 사용하는 무손실 코덱을 적용했다. 이 후보는 모든 시나리오에서 변경분 JSON보다 컸다. 바이너리가 항상 불리하다는 뜻은 아니며 정수 패킹·다른 스키마 최적화는 측정하지 않았다.

승계용 주기적 전체 상태는 1Hz로 유지한다. 무기 명령에 의해 추가로 발생하는 전체 상태도 유지한다. 변경분은 직전 일반 패킷이 아니라 마지막으로 확인된 전체 상태를 참조한다. 확인 지연은 250ms로 가정했고 확인된 기준이 없으면 전체 상태로 대체했다. 수신자마다 지연이 다른 경우는 다루지 않았다.

## 결과

단위는 **Mbps = 초당 페이로드 바이트 × 8 / 1,000,000**이다. 실제 네트워크 헤더·재전송·혼잡 시 드롭이 포함된 업로드 계측값이 아니라 게임 상태 배포에 필요한 데이터량이다.

| 시나리오 | 현재 방식 | 변경분 JSON | 변경분 + 전체 상태 경량화 | 마지막 후보의 감소율 |
| --- | ---: | ---: | ---: | ---: |
| 전원 대기 | 1.00 | 1.00 | 0.38 | 62.4% |
| 1명 이동 입력 | 9.69 | 1.23 | 0.57 | 94.1% |
| 4명 이동 입력 | 14.44 | 1.61 | 0.95 | 93.4% |
| 16명 이동 입력 | 14.44 | 2.75 | 2.08 | 85.6% |
| 4명 이동·무기 사용 | 17.49 | 4.58 | 2.57 | 85.3% |
| 16명 이동·무기 사용 | 30.86 | 18.65 | 12.24 | 60.3% |

전원 대기는 현재도 일반 프레임 대부분이 생략된다. 여기서의 62.4% 개선은 전체 신뢰 상태의 필드명을 반복하지 않는 효과다. 기존 8,912→8,008바이트 개선을 이번 개선율에 다시 합산하지 않았다.

무기 시나리오의 전체 신뢰 상태는 30초 동안 4명 조건 97회, 16명 조건 316회였다. 단순 1Hz의 30회보다 많다. `handleCommand`가 성공 시 `publishWorld(true)`를 호출하기 때문이다. 따라서 일반 프레임만 변경분으로 바꾸면 무기가 활발한 조건의 절감률은 39.6%로 낮아진다. 전체 신뢰 상태 형식과 명령별 전체 발행을 함께 검토할 이유다. 명령별 발행을 병합하는 개선은 이번 수치에 포함하지 않았다.

## 후보 코덱 검증

- 변경분 1,937개의 재구성 결과가 해당 시점의 원본 전송 상태와 일치했다. 전체 경량 상태도 각 발행 시 원본과 비교했다.
- 한글·이모지, 플레이어 추가·삭제를 재구성했다. 다른 기준 순번을 참조한 패킷은 거절하는 것을 확인했다.
- 매 20번째 변경분을 수신 갱신에서 제외하는 모형에서 97개를 제외했고, 그 다음 수신 갱신 93회가 직전 변경분 없이 전체 기준으로 복원됐다. 마지막에 제외돼 다음 패킷이 없는 경우는 다음 갱신 검사가 없다. 실제 패킷 손실·순서 뒤바뀜·신뢰 채널 지연 테스트는 아니다.
- 이 코덱은 측정용 시제품이다. 서비스 적용에는 통신 버전, 크기·범위 검증, 수신자별 확인 기준, 기준 만료, 재접속·승계·혼잡 처리를 구현하고 별도로 검사해야 한다.

## 참가자 중계의 별도 계산

전체 상태를 15명에게 직접 보내는 대신 일부 참가자에게 보내고, 이들이 나머지에게 동일 상태를 한 번씩 전달하는 2단계 트리의 산술 비교다. 실제 중계 기능을 구현·측정하지 않았다.

| 방장이 직접 보내는 중계 참가자 | 방장의 상태 배포 데이터 감소 | 중계 참가자 1명이 맡는 최대 추가 전달 수 |
| --- | ---: | ---: |
| 2명 | 86.7% | 7명 |
| 3명 | 80.0% | 4명 |
| 4명 | 73.3% | 3명 |

총 상태 전달 경로는 여전히 15개다. 방장의 부담을 다른 참가자에게 분산하는 효과이며 전체 네트워크 데이터량이 같은 비율로 감소하지 않는다. 일부 참가자의 상태 수신에는 한 번의 중계 지연이 추가되고 중계자 이탈·복구·권한 검증이 필요하다. 이 비율을 코덱 절감률과 더해서 해석하지 않는다.

## 해석과 다음 확인

측정한 조건에서는 전송 형식과 변경분 처리만으로 이동 위주의 85.6~94.1%, 무기가 활발한 조건의 60.3~85.3% 데이터량 감소 가능성을 보였다. 이 범위는 다른 플레이 양상에서도 보장되는 상한·하한이 아니다. 우선 전송 형식과 기준 상태 복구를 구현하고, 무기 명령 직후 전체 상태 발행을 안전하게 병합할 수 있는지 검토하는 순서가 타당하다.

통신 헤더·암호화·신뢰 전송의 재전송, HTTP 로비, 이동 입력·수신 확인·명령 응답·채팅·음악·초기 접속 데이터는 제외했다. 현재 소켓 대기열의 드롭·종료 동작도 이번 발행량에 반영하지 않았다. 실제 회선 업로드·지연·FPS·CPU 개선율은 알 수 없다. 변경분을 수신자별로 관리하면 CPU와 메모리가 더 필요할 수도 있다.

적용 후에는 16개의 실제 연결에서 양방향 바이트, 입력 반영 지연의 중앙값·95백분위, 버퍼 크기·드롭·재전송과 방장 CPU를 기록해야 한다. 느린 수신자·무기 연사·연쇄 들기·기준 상태 유실·방장 이탈을 포함하고, 실제 인터넷·TURN 사용 환경은 별도 확인한다.

## v9 적용 코드 비교

`web/`에서 `npm.cmd run test:metrics:p2p`로 재현한다. 원본은 로컬 `outputs/p2p-applied-benchmark.json`에 기록했다. 이전 시제품은 v8 발행 규칙을 고정한 역사적 비교로 유지하고 적용 코드 측정과 분리했다.

실제 v9 `tick`·코덱·대기열·수신 확인 처리를 사용한다. 게임 물리 30Hz, 30초, 수신자 15명, 수신자별 확인 지연 250/350/450ms, 주기적 전체 체크포인트 1Hz다. 명령은 실제로 적용하고 명령별 전체 전송을 다음 틱의 신뢰 상태 알림으로 합친다. 채널은 모형이며 일반 패킷 일부의 수신을 제외한다. 각 패킷을 실제 `WireReceiver`로 복원하고 15명 모두의 체크포인트 수신 확인을 검사한다.

비교 기준은 같은 물리 상태에서 v8의 전체 JSON·명령별 즉시 전체 발행·대기 중 중복 억제 규칙으로 계산한다. 앞부분 시제품의 15Hz 물리 호출과 이번 30Hz 물리 호출은 충돌·정지·명령 성공 횟수에 차이를 만들기 때문에 이전 표의 수치를 이번 수치와 직접 빼서 추가 개선율로 해석하지 않는다.

| 조건 | v8 상태 배포 요구량 | v9 적용 경로 | 감소율 |
| --- | ---: | ---: | ---: |
| 전원 대기 | 1.00 Mbps | 0.38 Mbps | 61.9% |
| 1명 이동 입력 | 4.97 Mbps | 0.52 Mbps | 89.4% |
| 4명 이동 입력 | 14.44 Mbps | 1.06 Mbps | 92.7% |
| 16명 이동 입력 | 14.47 Mbps | 2.29 Mbps | 84.2% |
| 4명 이동·무기 사용 | 17.57 Mbps | 1.90 Mbps | 89.2% |
| 16명 이동·무기 사용 | 29.31 Mbps | 6.38 Mbps | 78.2% |

전원 대기 50%·16명 이동 80%·16명 무기 50% 이상의 데이터 절감 목표를 통과했다. 현재 전송·수신·복구 구현을 사용하지만 실제 네트워크 계측을 대신하지 않는다. 입력·채팅·HTTP·암호화 헤더·재전송은 이 표에서 제외했으며 CPU와 FPS를 측정한 표도 아니다.

별도의 실제 루프백 RTC 검사에서는 장비 변경 명령→다른 참가자의 상태 반영 30회에서 중앙값 23ms·95백분위 52ms를 기록했다. 초기 방장의 인코딩 475회 누적 시간은 24.8ms였다. 네트워크·전체 시뮬레이션·렌더링의 CPU 개선율은 측정하지 않았다. 테스트는 사용자 브라우저를 조작하지 않았고 실제 인터넷·TURN·모바일 지연을 대표하지 않는다. 최종 배포·검사 근거는 [검증 기록](validation.md#p2p-전송-v9-구현검증배포-2026-11-04)에 둔다.
