# 불멍 놀이터의 제품 방향

2026-11-04 보호 제거 승인까지 반영한 제품 방향. 결정의 근거·범위·보류·충돌 처리는 [의도 기준](project-intent.md)을 따른다. 현재 구현의 설명은 [구조 문서](architecture.md), 검증 근거는 [검증 기록](validation.md), 의도와 구현의 차이는 [제품 검토](product-review.md)에서 관리한다. [초기 계획](plan.md)은 변경 전 결정의 기록이다.

## 사용자가 확정한 목적

> 인디게임개발자 디스코드 커뮤니티에서 사람들이 함께 온라인에서 온기를 느끼고 놀 수 있는 하나의 불멍 놀이터를 만든다.

2026-11-04 의도 인터뷰에서 사용자는 다음 장면을 **모두 보고 싶다**고 답했다. 이 답변이 기능별 개발 순서나 같은 비중의 화면 배치를 확정한 것은 아니다.

| 원하는 장면 | 경험을 검토할 때 볼 것 | 현재 이를 돕는 구현 |
| --- | --- | --- |
| 말없이 곁에 앉아 쉬기 | 대화나 조작을 계속하지 않아도 함께 있는 느낌이 드는가 | 앉기, 캐릭터와 이름, 모닥불, 개인별 소리 설정 |
| 이야기하며 장난치기 | 움직임과 반응이 귀엽고 서로 놀이를 이어 갈 수 있는가 | 채팅·말풍선, 감정표현, 달리기·점프, 연쇄 들기, 장난감, 트램펄린 |
| 각자 개발하다 잠깐 만나기 | 각자 작업하면서도 상호작용하고 돌아왔을 때 친구를 알아볼 수 있는가 | 같은 방에 머물기, 작업 메모·수동 상태·호출, 필드 보기·줌·PIP, 개인별 음악 듣기 |
| 만든 게임을 보여 주고 이야기하기 | 소개와 반응이 자연스럽게 오가는가 | 일반 채팅; 게임 전시·화면 공유·피드백 보관 전용 기능은 없음 |

위의 검토 기준은 목적을 관찰 가능한 질문으로 풀어 쓴 것이다. 실제 커뮤니티 사용을 통해 기준을 보완한다. 전용 기능을 모두 만들어야 한다는 요구로 해석하지 않는다.

## 휴식과 놀이의 관계

사용자는 장난과 휴식이 충돌할 때의 원칙으로 **휴식과 놀이 공간 구분**을 선택했다.

- 휴식과 적극적인 놀이가 함께 가능하도록 공간을 구분하는 방향으로 설계한다.
- 이미 승인된 총·눈뭉치·폭탄의 밀림, 들기·던지기·공중 잡기를 단지 ‘온기’라는 이유로 제거하지 않는다.
- 현재는 한 캠프장에 물리와 상호작용 규칙이 공통 적용된다. 휴식 구역, 경계 판정, 구역별 장난 차단은 **아직 구현하지 않았다**. 개인의 들리기 허용 해제는 공간 구분을 대신하지 않는다.
- 구역의 모양·크기, 처음 입장할 위치, 경계의 표시, 투사체·폭발·연쇄 들기의 경계 통과 방식은 미정이다. 공간 구분 원칙만으로 이 세부 동작까지 승인된 것으로 보지 않는다.
- 후속 답변으로 작업 중·자리 비움의 상태 기반 보호는 제거했다(INT-02). 공간 구분 전체를 취소한 답으로 확대하지 않으며, 구역 설계는 이번 범위에 포함하지 않는다.

## 현재 제품의 경계

- 웹에서 공개방 목록·초대 링크·코드로 최대 16명이 만나는 일시적인 캠프장이다. 게스트 입장이 가능하다. 새 방은 공개방과 목록에 없는 초대방을 선택하며 기존 방은 자동 공개하지 않는다. 공개방은 커뮤니티 소속 확인 없이 누구나 입장할 수 있다.
- 게임 상태 전송과 판정은 P2P를 유지한다. 네트워크 개선 논의에서 사용자가 서버 중심 전환에 이의를 제기했고, P2P 전송 최적화의 구현·검증·배포를 승인했다. 로비·인증·접속 협상의 서버 역할과 게임 데이터 중계를 구분한다.
- Discord는 프로필 사진 연결에 사용한다. 커뮤니티 소속 검사, 자동 음성방 입장, Discord Activity는 구현하지 않았다. 음성 대화는 기존 Discord 통화를 사용한다.
- 방장 이탈 시 같은 코드 안에서 후임에게 승계한다. 전원이 떠난 뒤에도 유지되는 공용 광장이나 영구 저장소는 아니다.
- 소리·음악 듣기·들리기 허용은 개인별 선택이다. 작업 중·자리 비움은 상호작용을 막지 않는다. 상태 변경은 앉기·공중 동작·들기 연쇄를 강제 변경하지 않는다. 앉은 상대는 들 수 없고 앉아서 다른 사람을 들 수도 없다. 피격 거부 설정이나 휴식 구역 기능은 없다.
- 대화를 기본 패널로 두고 사람·내 상태·놀이를 전환한다. 작은 화면과 필드 보기에서는 하단 메뉴로 패널을 열고 닫는다. 초대 정보는 펼쳐 보고, 긴 메모는 참가자 상세에서 읽는다.

## 이후 의도 확인이 필요한 결정

다음 항목은 미정 목록이다. 관련 작업의 결과가 사용자 결정에 달려 있을 때 구체적인 상황과 선택지를 제시한다. 목록 전체를 한꺼번에 질문하거나 자동으로 구현하지 않는다.

| 결정할 내용 | 영향을 받는 설계 |
| --- | --- |
| 같은 캠프 안의 구역인지, 별도 공간 사이의 이동인지 | 친구를 계속 볼 수 있는 범위, 동기화·입퇴장 구조 |
| 향후 공간 구분을 구현할 때의 경계 규칙 | 발사·피격·폭발·들기·던지기·소리·시각 효과의 처리. 이번 상태 보호 제거와 별도이며 보호를 현재 구현 요구로 추론하지 않음 |
| 공개방의 커뮤니티 회원 제한과 상설방 필요 여부 | 공개 목록은 구현했으며 현재는 누구나 참여·전원 퇴장 시 종료. 회원 검사·영구 방 수명은 미정 |
| 게임 소개와 추가 음성 경험에 필요한 보조 기능 | 작업 상태·호출은 구현. 게임 링크·소개 기능은 사용자 보류, 전시·화면 공유·자체 음성은 별도 결정 |
| 공개방 관리 수단 | 강퇴·차단·신고 등은 사용자 보류. 이번 범위에서 추가하지 않음 |

## 방향을 갱신하는 방법

기능 완료나 제품 검토 요청을 계기로 관련 구현과 실제 흐름을 이 문서의 장면에 대조한다. 첫 검토는 전체 구조를 훑고, 이후에는 변경 부분과 영향 범위를 중심으로 확인한다. 방향 전환이나 공통 상태·입퇴장 변경은 검토 범위를 넓힌다.

관찰한 사실, 사용자가 확정한 의도, AI의 제안과 미정 사항을 구분한다. 질문은 다음 결정에 필요한 만큼만 하고, 답변을 받은 항목만 확정 기준에 반영한다. 이미 승인된 내용을 다시 승인받거나 매 작업마다 질문 횟수를 채우지 않는다. 빌드·테스트 통과와 ‘함께 있는 온기’를 확인한 실제 사용 결과는 별도로 기록한다.

## 공개방과 작업 동석 계획 승인 (2026-11-04)

아래는 당시 승인 기록이다. 이 중 AFK 보호 선택은 후속 INT-02 결정으로 대체되어 현재 제공하지 않는다.

피드백 검토 후 사용자가 공개방 목록을 추가한 단계별 계획의 구현·검증을 승인했다. 작업 상태는 수동으로 정하고 입력 부재를 자동 AFK로 해석하지 않는다. AFK 보호·장난 허용과 호출 수신을 선택하고, 채팅·호출의 날짜와 시각을 표시한다. 작은 화면은 웹 필드 보기와 지원 환경의 Document PIP부터 제공한다. 데스크톱 독립 앱, 수동 방장 지정, 영구 기록·종료 후 푸시 알림은 이번 구현 범위에 포함하지 않는다. 음성은 [기술 검토](voice-options.md)까지 진행했고 실제 도입 방식은 확정하지 않았다. 구현·로컬 검증과 공개 사이트 배포는 별도 상태다.

## 축구공·작업 시간·백그라운드 계획 승인 (2026-11-04)

사용자가 축구공 접촉 놀이, 채팅의 오래된 순서부터 아래로 쌓기, 본인의 작업 시간, 수동 상태 표시 보강과 백그라운드 문제 개선 계획을 승인했다. 작업 시간은 이번 입장의 ‘작업 중’ 상태 구간을 개인에게 누적 표시하고 다른 창에서 개발하는 시간도 포함한다. 대화 가능·자리 비움에서는 멈추며 영구 작업 통계는 포함하지 않는다. 공은 걷기와 달리기로 차는 놀이이며 골대·점수·팀전은 이번 범위 밖이다.

소리 방식은 사용자가 **YouTube 작은 창**을 선택했다. 표시되는 공식 플레이어를 Document PIP에 두는 방식을 사용한다. 필드 PIP와는 번갈아 사용하고, 주 창 종료와 기기 절전 중 지속 실행을 보장하지 않는다. 휴식·놀이 구역은 이번에도 구현하지 않았으며 공간 분리 원칙과 세부 미정 사항은 유지한다. 공개 배포는 이번 구현·검증 승인에 포함하지 않는다.

## 전체 피드백 이후 변경 승인 (2026-11-04)

사용자는 작업 중에도 상호작용하기를 원하며 최종적으로 **보호 기능 제거 후 진행**을 선택했다. 이에 따라 기존 자리 비움 보호를 제거하고, 사람·상태·채팅의 접근성과 필드 상태 표식의 가독성을 개선한다. 관리 기능과 게임 소개 확장은 보류한다. 의도 문서·프로젝트 하네스·스킬을 함께 구성하되 AI의 주관과 자료가 사용자 목적을 대신하지 않도록 한다. 상세 범위와 변경 절차는 [의도 기준](project-intent.md)에 둔다.
